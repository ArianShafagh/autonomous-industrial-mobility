## What the project is

A master's thesis system: *"Towards Autonomous Industrial Mobility: An AI Framework for Optimal Path Planning and Resource-Efficient Navigation."* A TurtleBot-class AMR drives a factory maze in Gazebo, collecting parts from three production lines (A/B/C) and delivering them, deciding for itself what to do next under battery, payload, heat and wear constraints. Built on a copy of the older `robofetch` workspace, fresh git history, ROS 2 Jazzy + Gazebo Harmonic + Nav2.

## The structure

Ten ROS packages under `src/`, but the real organizing idea is **one model, three consumers**:

| Layer | Where | Role |
|---|---|---|
| Truth | `robofetch_factory/config/layout.yaml`, `params.yaml` | ASCII maze grid + every tunable number, each with unit and justification |
| Generation | `scripts/generate_world.py` | emits the Gazebo world, Nav2 map, POIs and the shortest-path matrix from that one grid |
| Physics/economics | `robot_model.py`, `factory_model.py` | pure Python, no ROS — energy, thermal, wear, production/blocking/faults |
| Execution | `mission_executor`, `mission_plan.py` | drives Nav2, recovery ladder, logs predicted vs measured |
| Decision | `robofetch_ai/policies/` | rule, symbolic, neural scorer, neuro-symbolic, PPO |
| Fast sim | `env/factory_sim.py` | same actions, same energy model, same path matrix, no Gazebo — a shift in 0.07 s vs ~30 min |
| Live bridge | `env/live_state.py` | wraps real ROS topics in the *same* interface as the fast sim |
| Serving | `robofetch_ai/service.py` :8001, `robofetch_bridge/app.py` :8000 | decision HTTP service + read-only dashboard |

The discipline that holds it together: the fast simulator and the live robot present an identical `state()` / `legal_actions()` interface, so the deciding code is literally the same object in both. That's validated numerically — replaying a real Gazebo mission in the fast sim matched within **0.6%** on distance/time/energy.

## The real problems, and the fixes

There isn't one problem; there's a chain, and each was caught by measurement rather than intuition.

**1. The hidden pinch (WP1).** A 0.5 m slot in the maze. Nav2 only marks 0.22 m around obstacles as lethal, so the *planner* routed through a gap the *controller* couldn't drive — the robot went 24.4 m instead of 10 m. This had broken the old project too. Fix: widen it, and add a generator check that compares paths in "comfortable space" vs "any space ≥ 0.25 m clearance" and refuses to emit a layout where the second is >5% shorter. Validated by feeding the broken layout back in — it flagged exactly the three pairs Nav2 got wrong.

**2. Numbers that were physically wrong (WP2 revision).** Drive energy was 0.35 Wh/m — 490 W for a 4.3 kg robot, 70× too high. Motor heating hit 70 °C in a minute. Fix: every number moved into `params.yaml` with a justification comment, with a sanity test (`test_realistic_magnitudes`) that catches magnitude errors — it immediately caught the author's *own* corrected value being 3.6× off. Consequence worth noting for the thesis: with honest numbers, **6 of 7 Wh per hour is idle electronics**, so energy efficiency is about time and batching, not metres.

**3. CPU starvation masquerading as a Nav2 bug (WP3).** Bringup hung on lifecycle timeouts. Cause: a 1 ms physics step meant 1000 Hz `/clock`, and every Python sim-time node burned ~55% CPU processing it; load average 14 on 12 cores, service replies dropped. Fix: 4 ms step, three section nodes merged into one process, single-threaded executor. Load 14 → 3.1.

**4. Nav2 reporting SUCCESS without arriving (WP3b).** With the goal blocked, the planner's 0.5 m tolerance lands the robot on the nearest free spot and declares success — a pickup "succeeded" with a box sitting on the target. Fix: verify arrival against the robot's *own AMCL pose* (not Gazebo ground truth, since a real robot has none), plus a recovery ladder (clear costmaps → back up → give up → return to charger → halt).

**5. The central one — the network overruling the rules (WP5→WP9).** This is the thesis's actual result. The neuro-symbolic model was best or tied almost everywhere, yet pooled it scored *below its own symbolic layer* (51.1 vs 52.9, p = 0.005). Almost all of the loss came from one unseen scenario, `heavy_load`: 28.5 vs 53.2. The trace showed the robot choosing `WAIT:60` eight times in a row while all three lines were BLOCKED — its own explanation string said waiting away from the charger just spends energy. The symbolic estimate was correct; the learned correction (+20 on every action, differences of ~7) simply swamped it. In training, production runs half as fast and batching pays; the network carried that habit into an overload it had never seen.

Fix: **bound the neural correction** — centre it on the candidates' mean and clip to ±1 score unit, chosen on training scenarios and validation seeds only. The network still decides close calls but can't overrule clear symbolic evidence. Pooled 51.1 → 53.6, unseen 42.4 → 46.8, 0/360 violations. An "unfamiliar input" guard via feature z-scores was tried first and **rejected** — rare binary features give |z| ≈ 13 even in training scenarios, so it carries no signal. That negative result is logged, which is the right instinct.

**6. The planner that won the benchmark and lost in operation (WP8 → WP9).** Theta* won on 7-leg tours: −3.3% time, p = 0.001, least turning, fastest planning. Made default. Then full 20-minute shifts showed it faulting in 6 of 17 runs — `"Either of the start or goal pose are an obstacle!"` — because Theta* has no start/goal tolerance, and the robot's own pose momentarily inside the inflation layer is fatal. NavFn plans from the nearest free cell within 0.5 m and faulted 0 of 5. A controlled alternating check (5 shifts each, interleaved so machine load hits both) confirmed it isn't CPU starvation, and that Theta*'s advantage vanishes over whole shifts (18.07 vs 17.75, sd ≈ 1.4). Default reverted to NavfnDijkstra. The honest conclusion is stated: *a planner chosen on short benchmark tours was the worse choice in operation, and only full-shift runs could expose it.*
